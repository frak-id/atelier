## How a template becomes a spawn

A `Template` is a small declarative record. A pure `templateToRequest(template)`
builder turns it into a `CreateSandboxRequest` using the **existing compose SDK**
— we do **not** hand-write processes/ports/provider JSON in the catalog:

```ts
import { composeOpencode, composePi, PRESETS, mergeSpecs } from "@atelier/compose";
import type { CreateSandboxRequest, SandboxSpec } from "@atelier/spec";

function templateToRequest(t: Template): CreateSandboxRequest {
  const fragments = [
    t.harness === "pi" ? composePi() : t.harness === "opencode" ? composeOpencode() : {},
    ...(t.surfaces ?? [])
      .filter((s) => s !== "terminal")            // terminal is always present
      .map((s) => PRESETS[s]()),                  // vscode() / browser()
  ];
  const merged = mergeSpecs(...fragments);        // SpecFragment
  const spec: SandboxSpec = {
    source: t.source,
    resources: t.resources,
    ...merged,                                    // processes, ports, files, annotations
    ...(t.hooks ? { hooks: t.hooks } : {}),
    metadata: { "atelier.dev/template": t.id },
  };
  return { ...spec, ...(t.toolboxes?.length ? { toolboxes: t.toolboxes } : {}) };
}
```

Notes that keep templates honest:
- **Models / provider config:** never written by the template. The org's
  **cliproxy** provider config is injected by the server seam / default toolbox
  (see `control/enrichment.ts` + `opencodeMergeProxyProviders`). Templates just
  pick the harness.
- **Binaries:** `opencode` + `code-server` come from the **auto-injected default
  org toolbox**; browser (`kasmvnc`/`openbox`/`chromium`) is **baked into
  `dev-base`**. So templates need no `build[]` except **pi** (recipe unknown →
  TODO inline toolbox).
- **Base images available:** `dev-base`, `dev-cloud`, `dev-rust` (from
  `infra/images/`). Exact registry-qualified tags are a TODO.

## The `Template` type

```ts
interface Template {
  id: string;
  name: string;
  description: string;                 // plain-language, operator-friendly
  category: "agent" | "editor" | "base" | "workstation";
  persona: "operator" | "builder" | "both";
  icon: string;                        // lucide-react icon name
  source: { image: string } | { snapshot: string };
  resources: { vcpus: number; memoryMb: number };
  harness?: "opencode" | "pi";
  surfaces?: ("vscode" | "browser" | "terminal")[];
  toolboxes?: string[];                // tb/<org|user>/<id>/<slug> selectors
  inlineToolbox?: ToolboxConfigInput;  // only when a template must install its own tool (pi)
  hooks?: { postCreate?: string[]; postStart?: string[]; onResume?: string[] };
  notes?: string;                      // caveats / TODO surfaced in Builder lens
}
```

## Staging-verified reference (pi + opencode)

Straight from the working staging helpers (`/tmp/pi-toolbox-def.json`,
`/tmp/spawn-pi-cliproxy.ts`, `/tmp/spawn-v2.ts`) on
`atelier.hetzner-staging.frak.id`. Treat these as ground truth over the SDK
defaults where they differ.

**Base image:** `dev-base-v2` (with `resources.diskGb: 20`). This is the real
tag; `dev-base:latest` in the catalog above is a placeholder — use `dev-base-v2`.

**pi toolbox** (built via `POST /v1/toolsets` → toolset ref
`toolsets/tb/user/18531342/pi@sha256:ff8b…`): the `build[]` in the Pi template
above, plus these two file-writing steps (verbatim intent):
- `~/.config/pi-cliproxyapi/config.json` →
  `{ proxy: { endpoint: "https://cliproxy.nivelais.com/v1", apiKey: "!cat ~/.config/pi-cliproxyapi/key", providerPrefix: "cliproxy" }, builtinProviders: { anthropic: { enabled: true, models: ["claude-sonnet-4-6"] }, openai: { enabled: true, models: ["gpt-5.4-mini"] } } }`
- `~/.pi/agent/settings.json` → merges the installed `packages`, sets
  `defaultProvider: "anthropic"`, `defaultModel: "claude-sonnet-4-6"`,
  `quietStartup: true`.

**pi harness process** (what actually spawns a working pi sandbox):
```json
{ "name": "acp", "command": "/home/dev/.local/bin/pi-acp", "cwd": "/home/dev",
  "user": "dev", "stdio": "bridge", "primary": true,
  "env": { "PATH": "/home/dev/.local/bin:/usr/local/bin:/usr/bin:/bin", "HOME": "/home/dev" } }
```
with `annotations: { "atelier.dev/harness": "opencode" }` (spoofed so pi-acp
rides the opencode ACP session surface) and the cliproxy key delivered as a
`0600` file:
`{ path: "/home/dev/.config/pi-cliproxyapi/key", content: <KEY>, owner: "dev", mode: "600" }`.

> **`composePi()` gap:** the SDK composer emits bare `command: "pi-acp"` relying
> on a login-shell PATH. The supervisor does **not** source a login shell, so
> staging uses the **absolute path + explicit `PATH`/`HOME` env**. Either fix
> `composePi()` to do the same, or have `templateToRequest` inject the env for
> the pi harness. Same applies to the `atelier.dev/harness` value — pi currently
> ships as `opencode` on purpose.

**opencode harness (staging smoke):** `command: "/opt/shared/bin/opencode acp"`
and `/opt/shared/bin/code-server …` — but note `dev-base-v2`'s Dockerfile has
**retired `/opt/shared`** in favour of `~/.local/bin` (org toolbox). The SDK's
bare `opencode acp` (relying on `~/.local/bin` PATH) is the intended path;
confirm which the current staging image actually resolves before shipping.
