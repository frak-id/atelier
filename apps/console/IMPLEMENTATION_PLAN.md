# Atelier Console — Implementation Plan (v2 redesign)

> Refines `UX_AUDIT.md` into a build plan scoped to what we're doing **now**.
> Grounded in the real data model (`@frak/atelier-shared` `AgentSession`,
> `AgentSessionStatus`, `AgentTodo`, permissions/questions) and the existing
> TanStack Query + Eden Treaty + Tailwind v4 + shadcn stack.

---

## Scope

**In scope (this pass)**
1. **Sessions-per-git-repo** in each sandbox, with per-session **todos**,
   organised cleanly. Empty groups hidden; sandboxes with no session get a
   small indicator.
2. **Real theme system** — colours, type scale, component microstates, empty
   states. Overall vibe generated via a **Gemini agent** pass (see §2.0).
3. **Short "mission control" home** — a list of **sessions**, and under it a
   list of **sandboxes**. No kanban/table toggle yet, no "needs input"
   monitoring (ACP can't surface it reliably — see §3.2).
4. **Operator vs Builder lens** — one persisted display preference over one data
   model.
5. **Onboarding / guidance** — selection-first flows, a **template gallery**,
   plain-language permission prompts, and a **block-based terminal**
   (AWS-IAM-policy-viewer feel).

**Explicitly out of scope (for now)**
- ❌ Chat UI. To *drive* an agent, we open the **harness's own UI** (the exposed
  sandbox URL, via the existing immersive iframe). We don't reinvent the wheel;
  the console orchestrates + monitors, the harness handles conversation.
- ❌ Command palette (`⌘K`) — deferred, not needed yet.
- ❌ Kanban / table density toggles — later.
- ❌ Plan-before-execute / autonomy dial — later (needs harness support).

## Data-model recap (what we can actually build on)

From `packages/shared/src/agent.schema.ts`:

| Shape | Fields we use | Notes |
|---|---|---|
| `AgentSession` | `sandboxId`, `id`, `parentID?`, `title`, `directory`, `time.{created,updated}` | `directory` = CWD = the cloned **git repo** (ACP needs a CWD). Grouping key. |
| `AgentSessionStatus` | `idle` \| `busy` \| `retry{attempt,message,next}` | Per session, keyed by id. No "needs input" state. |
| `AgentTodo` | `content`, `status(pending/in_progress/completed/cancelled)`, `priority?` | Per session. Fetched via `sessionTodosQuery`. |
| `AgentPermissionRequest` / `AgentQuestionRequest` | per **sandbox**, scoped by `sessionId` | The real "harness interaction" surface today. |
| `AgentEvent` (SSE) | coarse invalidation `{resource, sessionId?}` | Already wired in `use-agent-events.ts`; drives live updates. |

Existing queries (`api/queries/sessions.ts`) are **per-sandbox**. The home needs
sessions **across all sandboxes** → aggregate client-side with `useQueries` over
the sandbox list (§3.1). Flag a future server aggregate endpoint if N grows.

## Phase 0 — Theme & component foundation

*Biggest perceived-quality jump, least structural risk. Do this first.*

### 0.0 Theme — CHOSEN: "Graphite & Alabaster" (Gemini-generated)
Generated by a **Gemini `gemini-3.1-pro-preview`** agent (3 candidates: Midnight
Cobalt, Graphite & Alabaster, Glacial Onyx). Selected: **Graphite & Alabaster**
— warm-neutral, editorial, mono accent; reads premium/trustworthy to execs while
staying low-fatigue for long Builder sessions. Full 3-candidate exploration is
archived at `apps/console/design/theme-candidates.md`. Vibe: *premium editorial
workspace — understated, warm, highly trustworthy.*

### 0.1 Theme tokens — `src/index.css`
Replace the stock shadcn HSL set. Keep the same CSS-variable *names* (so
components don't change), add semantic status tokens, default to **dark**.

**Dark (warm-black ramp + inverse mono accent):**
```
--background        (app bg)      #1A1918
--card / --popover  (surface)     #22201F
--elevated                        #2D2B2A   /* dropdowns, modals, terminal chrome */
--border / --input                rgba(255,255,255,0.08)   /* hairline */
--foreground        (text)        #EDEDEC
--muted-foreground                #999591
--primary   (accent)              #EDEDEC   /* inverse: light on dark */
--primary-foreground              #141312
--ring                            rgba(237,237,236,0.30)
--success                         #2D8A66   /* running / done */
--warning                         #D48D3A   /* busy / attention */
--danger    (destructive)         #C45A5A   /* error / retry */
--info                            #6B8BBE   /* in review */
--radius                          0.5rem    /* 8px, soft */
```
**Light (alabaster):**
```
--background        #F5F4F1     --card/--popover   #FCFCFB     --elevated  #FFFFFF
--border/--input    rgba(0,0,0,0.08)             --foreground  #141312
--muted-foreground  #706D6B     --primary  #141312            --primary-foreground #FCFCFB
--ring rgba(20,19,18,0.30)      --success #287A5B  --warning #B5752E  --danger #A64444  --info #5072A8
```
Note: `--primary` is an **inverse** (light-on-dark / dark-on-light), so status
colour carries all the "meaning" hue — keep colour restrained elsewhere.
Ship a **`ThemeProvider`** (`src/providers/theme.tsx`) that applies
`.dark`/`.light` on `<html>`, persists to `localStorage`, respects
`prefers-color-scheme`. Small toggle in the header.

### 0.2 Type system
- **Geist Sans** (UI) + **Geist Mono** (code) — loaded via `@font-face`/package;
  wire `--font-sans` / `--font-mono` in `@theme`. Tabular numbers on all
  metrics/IDs/timestamps.
- Scale (px / line-height): `xs 12/16`, `sm 13/20` (dense Builder), `base 15/24`,
  `lg 18/28`, `xl 20/28`, `2xl 24/32`.
- Fix the **light-app / dark-terminal clash**: derive `terminal-view.tsx`
  `THEME` and `multi-terminal.tsx` `bg-[#09090b]` from the theme tokens via a
  `terminalTheme(theme)` helper using the harmonized palette:
  `bg` transparent/`--elevated`, `fg` `--foreground`; ANSI — red `#C45A5A`,
  green `#2D8A66`, yellow `#D48D3A`, blue `#6B8BBE`, magenta `#9D76B1`,
  cyan `#599B9A`, plus brights (see archived candidate file). Terminal now
  belongs to the app in both modes.

### 0.3 Component microstates (`src/components/ui/*`)
- Give **button/input/checkbox/card** all six states: default, hover, focus
  (designed ring, not `outline-hidden`), active/pressed, disabled, loading.
- Replace raw `<input type="checkbox" className="size-4">` (in
  `sandboxes.$sandboxId.index.tsx` expose-port, spawn) with the Radix
  `Checkbox`.
- Add primitives we'll need: **`Tabs`**, **`Tooltip`**, **`Badge`** status
  variants (`success`/`warning`/`danger`/`info`/`neutral`), **`EmptyState`**,
  **`SegmentedControl`** (for the lens toggle), **`StatusDot`**.
- Motion vocabulary (per chosen theme — deliberate & smooth, not snappy):
  **200ms linear** for colour/opacity fades, **400ms `cubic-bezier(0.2,0.8,0.2,1)`**
  for structural changes (cards/modals/flyouts), **2s calm pulse** for attention
  states. Soft diffuse elevation shadows (`0 12px 32px rgba(0,0,0,0.5)` dark /
  `0 12px 32px rgba(0,0,0,0.08)` light). Define as Tailwind utilities / keyframes.

### 0.4 Empty states
Create a reusable `EmptyState` (icon + title + one-line + primary CTA). Replace:
- Home "No sandboxes … next milestone" (stale) → "Spin up your first agent"
  → routes into the template gallery (§5).
- Spawn empty JSONC → selection-first (§5); JSONC becomes Builder-only advanced.
- Sessions "No agent sessions" → "Start a session in `<repo>`" linking to the
  harness UI.

**Acceptance:** app is dark by default, terminal matches chrome, one type
family, buttons/inputs have visible focus rings + loading states, no stray raw
checkboxes, empty states are actionable. `bun run typecheck` clean.

## Phase 1 — Sessions per repo + todos (the core)

### 1.1 New component: `SessionsByRepo`
Group `AgentSession[]` by `sandbox → directory (repo)`. Reuse the existing
`repoLabel(directory)` helper (trailing path segment). Within a repo, order by
`time.updated` desc; nest children under `parentID` when present (opencode).

Each **session row** shows:
- repo label + full `directory` (mono, muted),
- `title || "Untitled"`,
- **status chip** from `AgentSessionStatus` (idle=neutral, busy=warning+pulse,
  retry=danger `retry N`),
- relative `time.updated`,
- a **todo summary** inline: `▸ 3/7 · "writing tests"` (completed/total +
  current `in_progress` content). Full list on expand.
- actions: **Open** (→ harness UI, §1.3), Abort (busy only), Delete.

### 1.2 Todos
- Keep `sessionTodosQuery(sandboxId, sessionId)`. To avoid N requests on a big
  fleet: fetch todos **eagerly only for `busy` sessions**, lazily (on expand)
  for idle ones. Summary line uses whatever's cached; expand triggers fetch.
- Render with the existing `TODO_ICON` map; strike completed/cancelled.
- **Empty handling:** sessions with **no todos** show nothing (no empty box);
  repos/sandboxes with **no sessions** are **not rendered** in the sessions
  list — instead the sandbox surfaces a **small "no active session" indicator**
  in the sandboxes list below (§3).

### 1.3 "Open" = terminal (for now)
"Open" navigates into the sandbox's **immersive terminal** — reuse
`ImmersiveView` (extract from `sandboxes.$sandboxId.index.tsx` into
`src/components/immersive-view.tsx`, make it addressable so a session row can
deep-link to it). The terminal is the universal surface every harness has.

> **TODO (later):** Some harnesses expose an **iframe-able web UI** (opencode
> `serve`, or pi with certain plugins) — but it's per-sandbox and we don't
> reliably expose that URL in `sandbox.urls` yet. When we do, "Open" should
> prefer the harness web UI (iframe tab) and fall back to the terminal. Track:
> surface a `harnessUrl`/capability flag from the server, then branch here.

### 1.4 Live updates
Already handled by `use-agent-events.ts` SSE → query invalidation. The home
must subscribe per visible sandbox (see §3.1 perf note) so sessions/statuses/
todos refresh live.

**Acceptance:** sessions render grouped by sandbox→repo with live status + todo
summaries; empty groups hidden; "Open" lands in the harness UI; aborting/
deleting works and reflects live.

## Phase 2 — Operator vs Builder lens

### 2.1 Lens context
`src/providers/lens.tsx`: `useLens()` → `"operator" | "builder"`, persisted in
`localStorage`, default **operator** for new users. `SegmentedControl` in the
header ("Overview" / "Developer"). It's a **display preference, never a gate**;
destructive/consequential actions stay visible in both.

### 2.2 What each lens renders (one data model, two renderings)

| Surface | Operator | Builder |
|---|---|---|
| Home | Sessions + sandboxes, plain-language status ("Working…", "Idle") | + raw `busy/retry`, sandbox ids, harness badges |
| Spawn | **Template gallery** only (§5) | Templates + saved specs + **JSONC editor** |
| Sandbox detail | URLs, Sessions, Terminal, primary actions | + Processes, Expose port, Capture toolset, Metadata |
| Permissions | plain-language prompt (§5.2) | + raw `permission` string, glob `patterns`, metadata |
| Errors | one sentence + next step | full message / logs |

Implement by wrapping advanced sections in `{lens === "builder" && …}` and
swapping copy via small presenter helpers — **no route/data forks**.

**Acceptance:** toggling the lens instantly shows/hides advanced surfaces with
no reload; preference persists; nothing consequential is ever hidden.

## Phase 3 — Short mission-control home (`routes/index.tsx`)

### 3.1 Layout
Rewrite `/` as two stacked sections at `max-w-5xl`:
1. **Sessions** (top) — `SessionsByRepo` across the fleet. Aggregate via
   `useQueries` over `sandboxListQuery()` → `sessionsListQuery(id)` +
   `sessionStatusesQuery(id)` for each sandbox. Hide sandboxes with zero
   sessions here. Subscribe to `useAgentEvents(id)` per sandbox with sessions.
   - *Perf note:* fine for tens of sandboxes; if the fleet grows, add a server
     `GET /sessions/all` aggregate + a single SSE multiplexer. Leave a TODO.
2. **Sandboxes** (below) — the existing sandbox list (`SandboxRow`), restyled.
   Each row gets a **small session indicator**: a `StatusDot` + count
   (`● 2 sessions` / muted `○ no session`). Keep pause/resume/destroy.

Header: wordmark, lens toggle, theme toggle, org context, user/logout.

### 3.2 No "needs input" column (deliberate)
ACP doesn't reliably expose a "waiting on human" state, so we **don't** fake a
kanban "Needs input" lane. Permissions/questions still surface where they live
today (sandbox sessions view) and via the harness UI. Revisit when the harness
can signal it.

**Acceptance:** home shows live sessions grouped by repo up top, sandboxes with
session indicators below; empty session groups omitted; both lenses read well.

## Phase 5 — Onboarding, templates & block terminal

### 5.1 Template gallery (the non-technical on-ramp)
- New `src/lib/templates.ts` — the **curated static catalog** (Gemini-generated,
  hand-corrected) defined in `apps/console/design/templates.md`. Core five:
  **OpenCode Agent** (default), **VS Code + OpenCode**, **Browser Agent**,
  **Base Agent** (cliproxy base), **Pi Agent**; plus extras (Instant Workspace,
  Full Workstation, Ask-a-Codebase, Rust Agent).
- A pure **`templateToRequest(t)`** builder composes each template into a
  `CreateSandboxRequest` using the existing **`@atelier/compose`** SDK
  (`composeOpencode`/`composePi` + `PRESETS.vscode`/`PRESETS.browser` +
  `mergeSpecs`) — no hand-written processes/provider JSON, no new backend. It
  reuses the existing `spawnFromSpec` path.
- New `src/components/template-gallery.tsx`: cards (icon, name, plain-language
  description, surface chips, persona) → **one-tap Spawn**. Operator lens shows
  the top-3 default gallery; Builder lens shows the full grid **plus** dynamic
  prebuilds/saved-specs.
- **Instant Workspace** binds to `prebuildsListQuery` (one card per prebuild).
- First-run onboarding = selection flow: **pick a template → (repo/branch if the
  template needs one) → Spawn → land in the terminal**. No blank canvas.
- **Grounded on staging** (see templates.md §"Staging-verified reference"):
  base image = **`dev-base-v2`** (`diskGb:20`); the **pi toolbox recipe is now
  known** (npm `--prefix ~/.local` + pi plugin installs + cliproxy config/key
  files). Remaining: pi harness needs an **absolute `pi-acp` path + explicit
  `PATH`/`HOME` env** and rides `annotation harness=opencode` (fix `composePi()`
  or `templateToRequest`); repo-scoped templates thread a repo URL into a
  `postCreate` clone; confirm the raw cliproxy key is supplied by the seam, not
  the console.

### 5.2 Plain-language permission prompts
Rewrite `PermissionRow` / `QuestionRow` into a **what / why / risk / decision**
card for Operator lens:
- **What** — humanised `permission` label,
- **Risk** — low/med/high hint (derive from permission kind/patterns),
- **Decision** — `Allow once` / `Always` / `Reject` (existing replies).
Builder lens additionally shows the raw `permission` string, `patterns`, and
`metadata`. Same mutations (`useReplyPermission`, `useReplyQuestion`).

### 5.3 Block-based terminal (AWS-IAM feel)
Wrap `xterm` output into navigable **blocks** (command + output), with a subtle
left-border accent, copy-per-block, and jump-to-block. Structured, readable,
audit-trail style — the "AWS IAM policy viewer" calm. Build as a thin layer over
the existing `TerminalView`; keep raw scrollback available in Builder lens.

**Acceptance:** a non-technical user can go template → spawn → watch progress
→ answer a plain-language prompt without touching JSONC or infra; developers
keep full power in Builder lens.
